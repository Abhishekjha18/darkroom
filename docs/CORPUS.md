## 3. The two oracles that go in the README

Both are commands a judge can run. That is the point: it converts a soft *"look, it
renders"* proof into a hard pass/fail one.

| # | Check | Command | Verdict |
|---|---|---|---|
| 1 | **DEFLATE round-trip** | darkroom's compressed output through real `gunzip` | pass/fail |
| 2 | **PNG conformance** | every valid PngSuite file decodes; every corrupt one is rejected without panicking | pass/fail per file |

And two more that need no command at all:

| 3 | **`jpeg-js` pixel diff** | mean/max absolute difference, printed on every run | a number |
| 4 | **The QR code** | point a phone at it | **it scans or it doesn't** |

Oracle #3 is the one to wire in first — see `SPIKE-JPEG.md` §7.

## 4. The vendor-EXIF gap — narrowed, not closed

**The problem, as it stood:** everything in `pathological/` is *generated*, so every EXIF
block in the corpus was written by the same generator. That is a self-consistent oracle,
and a self-consistent oracle proves less than it appears to. `LLD-EXIF.md` §5 names two
bugs that only appear on big-endian files, and **nothing staged was big-endian at all**.

**What was added.** `exif-vendors/` — nine files built byte by byte by
`../../corpus/generate_exif_vendors.py`, deliberately imitating different makers rather
than one generator's habits:

| File | What it exercises |
| --- | --- |
| `canon-le.jpg` | Little-endian; model repeats the make, so the camera name must not become "Canon Canon EOS 5D" |
| `nikon-be.jpg` | **Big-endian**, orientation 6 — the left-justified inline SHORT trap |
| `sony-be-gps.jpg` | **Big-endian** GPS with awkward denominators (`3044/100` minutes, `0/1` seconds). Assuming `/1` lands you in the wrong ocean |
| `android-le-portrait.jpg` | Orientation 8, space-padded make (`"samsung   "`), no lens tag |
| `datetime-only.jpg` | Third rung of the date chain: `DateTime` only, no `DateTimeOriginal` |
| `no-date.jpg` | EXIF present, no date at all — must fall through to mtime |
| `unset-clock.jpg` | `"0000:00:00 00:00:00"` — must **not** become 1970 |
| `no-exif.jpg` | No EXIF whatsoever |
| `iphone-heic-container.heic` | ISOBMFF `meta` → `iinf` → `iloc` walk. Date, camera, lens and GPS read from a file whose pixels are never decoded |

**Why they are worth having:** every one is cross-checked **field by field against Pillow**,
an independent EXIF reader — 38 fields across the set, 2 of the files big-endian. A fixture
only darkroom agrees with proves nothing; Pillow parsing them proves the files are genuinely
well-formed rather than merely self-consistent. The check is
`oracles::exif_matches_pillow_across_vendors` and it fails the build if no big-endian
fixture is present.

### 4.2 What a real 414-file library proved

Run against a real OneDrive photo folder on 2026-08-19: 414 files, 638 MB, 398 images.

**396 of 398 decoded. The only two failures in the entire folder were GIFs** - a format cut
as "nice, not needed". That is what earned GIF its ~250 lines (`FEATURES.md` section 7.2),
and `gif/` now stages the cases: LZW at several code widths, interlacing, transparency,
an animation, 1x1, and an odd size. All eight are **pixel-identical to Pillow**.

The same run also measured what no fixture can: **8.1 s cold, 6 ms warm, 20 MB resident,
1679 req/s across 12 concurrent clients with zero errors**, and 40 duplicate clusters whose
members were checked by hand - every one a genuine near-duplicate, none byte-identical.

### 4.1 What real device files proved — and what they changed

On 2026-08-19 a folder of files from a real phone was tested against the decoder. Five
files, and they were worth more than their number suggests:

**One real HEIC, from a Samsung SM-A326B.** The synthetic `iphone-heic-container.heic` is
spec-shaped; the real file is not that tidy. `mdat` comes *before* `meta`, and it carries
`pitm`, `iprp`/`ipco`/`ipma`, `idat`, `iref` and a trailing vendor `sefd` box that the
fixture never had. **The `iloc` walk read it correctly** — date, camera, lens, exposure,
ISO, dimensions and GPS all recovered from a file whose pixels are never decoded. That is
the first time that code met anything it did not itself produce.

**Four progressive JPEGs, and a wrong assumption.** All four were SOF2 progressive, because
**WhatsApp re-encodes everything it sends that way**. `FEATURES.md` §2.9 had cut progressive
on the grounds that it was *"common on the web and rarer from cameras"*. In a real phone
gallery it is neither rare nor web-only — it is the single most common variant, and the
decoder returned `Unsupported` for every one. **Progressive is now implemented**
(`FEATURES.md` §7.1) and `progressive/` staged so the case stays covered.

⚠️ **Those four files also carried no EXIF at all** — WhatsApp strips it completely. That is
worth knowing for its own sake: a large share of a real gallery has no metadata, and the
timeline has to fall back to file time gracefully rather than treat it as an error.

### ⚠️ What is still missing

**These are hand-built files, not photographs from real cameras.** They cover the layout
variations the specification and the LLD name. They cannot cover what nobody documented:

- **Vendor MakerNotes** (tag `0x927C`) — every manufacturer invented their own undocumented
  format. Out of scope by decision (`LLD-EXIF.md` §8), but real files carry them and they
  change the shape of the IFD around them.
- **Real HEIC from a real iPhone.** The container here is spec-shaped and the box walk
  handles it, but Apple's actual `iloc` layout, `idat`-based construction methods and item
  ordering are unexercised.
- **Genuinely odd firmware.** Duplicate tags, out-of-order IFD entries, off-by-one counts —
  the things that only turn up in the wild.

**Cost to close: a handful of real photos** — Canon, Nikon, Sony, iPhone, Android, straight
off the camera or SD card. Not edited, not re-exported, and not sent through a messaging app,
all of which rewrite or strip the EXIF block and destroy exactly the variety that is the
point.

## 5. Also needed before recording

From `DEMO-SCRIPT.md` §pre-flight, and it is corpus work rather than code work:

- **A curated demo folder — JPEG only, thousands of files**, large enough to be convincing.
  Not twelve samples.
- **No HEIC in it.** The HEIC limitation gets disclosed at 4:30 on our own terms; a judge
  discovering it at 1:15 is a different thing entirely.
- **A genuine near-duplicate set inside it** — the same shot at two resolutions. Exact
  duplicates are unremarkable; near-duplicates are the thing people cannot do themselves.
